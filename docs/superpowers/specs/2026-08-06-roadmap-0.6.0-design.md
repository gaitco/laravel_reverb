# laravel_reverb — Roadmap 0.6.0

**Date:** 2026-08-06
**Status:** Approved
**Follows:** `docs/superpowers/specs/2026-08-06-roadmap-0.4-0.5-design.md`, whose 0.4.0 and
0.5.0 scopes both shipped. That document's "Explicitly not doing" list still stands and is
not revisited here.

## Goal

Finish what 0.5.0's split started and close the rough edges its reviews recorded. This
release adds no capability: everything in it is cleanup, and it is scoped that way
deliberately.

`emitFrame` is additive public API, which is why this is 0.6.0 rather than 0.5.1.

## Why now

The field-ownership work in section 1 is the only item here with a real deadline. 0.5.0
moved every method into a mixin but left all 29 fields on `_ReverbBase`, so the next field
anyone adds will land on the base by default and the boundary will be a little less true
than it was. That erosion is cheap to stop today and expensive to reverse once several
releases have built on it.

Nothing else here is urgent. It is grouped into one release because a cleanup release is
easier to review than cleanup smuggled into a feature.

## 1. Field ownership

Today `_ReverbBase` holds 29 fields, so `_ReverbHealth` can mutate `_generation` and
`_ReverbConnect` can mutate `_live`. 0.5.0's `on` chain documents which *methods* cross
mixin boundaries; nothing documents or constrains which *fields* do. The coupling that
actually produces bugs in this package — three near-identically-named epoch counters
reachable from anywhere — is exactly as it was before the split.

Dart mixins can declare instance fields, so each mixin can own the state only it mutates:

| Mixin | Owns |
|---|---|
| `_ReverbHealth` | `_live`, `_channelHealthController` |
| `_ReverbChannels` | `_channels`, `_generations`, `_clientEpoch` |
| `_ReverbConnect` | `_state`, `_shouldRun`, `_everConnected`, `_attempt`, `_generation`, `_states`, `_reconnectedCallbacks`, `_pausedByLifecycle`, `_observing`, `_reconnectCount`, `_connectedSince` |
| `_ReverbBase` | The 12 constructor-injected values, plus `_connection` |

`_connection` stays on the base deliberately. `_ReverbChannels._subscribe` and `_sendFor`
need it to send; `_ReverbConnect._open` and `_onDropped` need it to manage the socket.
Moving it into either mixin would make the `on` chain circular. Having it be the **only**
shared mutable field is a far stronger statement than today's shared-everything base:
after this change, one field is the seam, and it is named as such.

Two supporting moves:

- **`_resetPresenceRosters` migrates from `_ReverbHealth` to `_ReverbChannels`.** It walks
  `_channels` and calls `resetPresence()` on each `PresenceChannel` — a channels concern
  wearing a health label. Moving it leaves `_ReverbHealth` touching nothing but `_live`
  and its own controller, so that mixin depends on the base and nothing else.
  `_ReverbConnect` still reaches it through the `on` chain.
- **`disconnect(forget: true)` gets an interface instead of field pokes.** It currently
  does `_clientEpoch++`, `_channels.clear()` and `_generations.clear()` inline. Those three
  become one `_forgetAllChannels()` on `_ReverbChannels`, which is also where the comments
  explaining why each step exists belong.

### What this does and does not buy

It does not eliminate cross-boundary state access. Dart's `on` clause grants access to the
interface of the named types, fields included, so `_ReverbConnect` can still read
`_ReverbChannels`' state after this change — and in a few places it legitimately needs to.

What changes is that the access becomes **directed and compiler-enforced** rather than
ambient. Today any mixin can touch any field because they all live on the shared base.
After this, `_ReverbConnect` can reach channel state only because its `on` clause says so,
`_ReverbHealth` cannot reach it at all, and adding a new cross-boundary dependency means
editing an `on` clause — a visible, reviewable act.

That is a smaller claim than "the mixins are now encapsulated". It is the true one.

**Done when:** `_ReverbBase` declares 13 fields; `_ReverbHealth`'s `on` clause is
`on _ReverbBase` and it references no field it does not own; the public API is unchanged;
`test/exports_test.dart` is untouched; and the full suite passes with no test edited.

## 2. `ReverbFake` polish

**`emitFrame(Map<String, dynamic> frame)`.** Two independent reviewers noted the same gap
during 0.5.0: `emit` always builds a `{event, channel, data}` frame, so there is no way to
send anything else. Two things are currently unreachable —

- **Seeding a presence roster.** `PresenceChannel`'s member list is populated from a
  `pusher_internal:subscription_succeeded` frame carrying `presence` data. `ReverbFake`
  never sends one, so `here`/`joining`/`leaving` and `currentMembers` cannot be tested
  through it. Ordinary event dispatch on presence channels works today (dispatch does not
  gate on the ack), and nothing in the docs claims roster support — but the README does
  advertise presence channels, and a user will reasonably expect to test rosters.
- **Channel-less frames**, such as `pusher:error`. `emit('', 'pusher:error', ...)` happens
  to work, because `_onFrame` handles that event before reading the channel, but it reads
  as a hack because it is one.

`emitFrame` takes the frame as the server would send it and does nothing else. `emit` stays
as the ergonomic path for the common case.

**A real error before `connect()`.** `lib/testing.dart` uses `_socket!` in `emit` and
`drop`, so calling either before `connect()` throws `Null check operator used on a null
value` — a crash that names nothing useful, from a helper whose entire audience is people
writing tests. Replace both with a `StateError` naming the actual mistake.

**A worked roster example in the README.** The `## Testing your app` section should show
seeding a presence roster with `emitFrame`, since that is the one thing a reader cannot
derive from the rest of the section.

**Done when:** a test seeds a presence roster through `emitFrame` and asserts `here` fires
with the right members; calling `emit` before `connect` produces a `StateError` whose
message names `connect()`; and the README example runs as written.

## 3. Recorded coverage gaps

Three one-liners, each recorded during an earlier release's review and each deferred at the
time as correct-but-untested:

- **`path: '/'`** — an all-slashes path normalizes to `''` and produces `/app/KEY`. Traced
  by hand during the 0.4.0 review and confirmed correct; never asserted.
- **Cache miss on prefixed channels.** The end-to-end `pusher:cache_miss` test covers a
  plain `cache-` channel. `private-cache-` and `presence-cache-` traverse identical code —
  verified by reading it — but the README names all three, so the tests should too.
- **`exports_test.dart` cannot notice an accidental *extra* export.** Open since the 0.2.0
  roadmap. It is a hand-maintained compile check: it fails when something stops being
  exported, and stays silent when something starts being exported that should not be.
  Closing it means comparing the entry point's exported names against an expected list.

## 4. Open question: the Android cleartext claim

Not code, and not resolvable from this repository.

`README.md`'s "Local development" section says Android's cleartext restrictions apply from
API 28 and hedges on whether they affect this package. That hedge is deliberate: the
restriction is enforced by `NetworkSecurityPolicy` in the Java networking stack, while this
package's socket comes from `web_socket_channel` → `dart:io`, which opens sockets from the
Dart VM. Whether that path consults the policy was never established.

**The experiment:** `flutter run` a debug build against `ws://10.0.2.2:8080` on an API 28+
emulator with an unmodified `AndroidManifest.xml`. If it connects, the troubleshooting
checklist's item 2 is sending users after a phantom and should be softened further. If it
fails, the prose can state the mechanism outright instead of hedging.

Until someone runs it, the hedged wording stays. A README that says "may" where nobody has
checked is honest; one that says "does" would not be.

## Explicitly not in 0.6.0

Recorded so they are decisions rather than omissions:

- **Splitting `lib/src/connection.dart` (365 lines) or `lib/src/channel.dart` (332).**
  `connection.dart` grew during 0.5.0 and is now the largest file in the package. It holds
  the ping/pong/watchdog timer interactions, which are subtler and less covered than the
  epoch counters 0.5.0 moved, so a split there earns its own release and its own review
  attention rather than riding along with unrelated cleanup.
- **A Dart-only core.** The package's only Flutter dependency is `WidgetsBindingObserver`,
  used for app-lifecycle handling. Separating it would make the client usable from Dart
  servers, CLI tools and plain `dart test`. That is a real new audience and a structural
  change to how the package is consumed — it needs its own design pass, not a bullet in a
  cleanup release.
- Everything on the 0.4/0.5 roadmap's permanent won't-do list: encrypted channels, Pusher's
  hosted service and clusters, and client-side offline event replay.
