# laravel_reverb — Roadmap 0.7.0: none planned

**Date:** 2026-08-07
**Status:** Approved
**Follows:** `2026-08-06-roadmap-0.6.0-design.md`, whose scope shipped as 0.6.0.

## The decision

**There is no 0.7.0 planned.**

As of 0.6.0 the package has 146 tests, 1 example-app test, and no known gap against what a
self-hosted Reverb server actually implements. Public channels, private channels, presence
channels with rosters, client events, cache channels, custom server paths, reconnection with
re-authorization, app-lifecycle handling, connection metrics and a testing fake are all
shipped and reviewed.

Three candidates for further work exist. All three are internal polish on code that has
already been through hard review, and nobody has asked for any of them. They are parked
below with the trigger that would justify starting each one.

The next change to this package should be driven by a user, a bug, or a Reverb server
feature — not by a release cadence.

## Parked: a Dart-only core

Splitting the one Flutter dependency out, so the client works from Dart servers, CLI tools
and plain `dart test`.

**Feasibility is settled; packaging is not.** The coupling is shallower than it looks:

- `lib/src/connection.dart` imports `package:flutter/foundation.dart` for exactly one thing,
  the `@visibleForTesting` on `sendPingForTest`.
- `lib/src/reverb.dart` imports `package:flutter/widgets.dart` for `WidgetsBinding`,
  `AppLifecycleState` and `WidgetsBindingObserver`, used across roughly thirty lines in
  `lib/src/reverb_connect.dart` (`addObserver`, `didChangeAppLifecycleState`) and one line in
  `lib/src/reverb.dart` (`removeObserver`).

The open question is what to ship: one package whose lifecycle handling becomes an optional
Flutter add-on, or two packages. That is a decision about who the package is *for*, and it
needs its own design pass rather than a bullet in a cleanup release.

**Trigger:** someone wants the client outside Flutter. Until then this is speculative
audience-building.

## Parked: splitting `lib/src/connection.dart`

At 365 lines it is the largest file in the package, and it grew during 0.5.0 when metrics
recording landed in it.

**It has a genuine seam, unlike the `Reverb` split.** The keepalive — four timers
(`_idleTimer`, `_pongTimer`, `_pingTimer`, `_watchdogTimer`), plus `_onActivity`,
`_startPingLoop`, `_sendPing`, `_armPongDeadline`, `_restartIdleTimer` and `_stopTimers` —
communicates with the socket through only two things: send a ping, and declare the socket
dead. That is a small enough interface to extract as a real collaborator class in its own
library, rather than another mixin in a `part` file.

That would be a better outcome than either of the previous two splits achieved, because a
separate library gets real privacy (see the next section for why that matters).

**Trigger:** a bug in the timer interactions, or the file growing again. The timers are the
subtlest and least-covered code in the package, which is an argument both for splitting it
and for not doing so casually alongside unrelated work.

## Parked: sealing the epoch counters

The thing 0.5.0 and 0.6.0 structurally could not do.

`_generation` (connect loop), `_generations` (per channel name) and `_clientEpoch` (per
client) are near-identically named and guard different races. 0.5.0 moved the methods into
mixins; 0.6.0 moved the fields to their owners. Both made access **directed** — a mixin
reaches another's state only because its `on` clause says so. Neither made it **impossible**,
and neither could: `part` files all share one library, and Dart privacy is library-scoped, so
a private field is visible to every part of the library that declares it.

Real encapsulation needs a separate library — a plain `import`ed file, not a `part`. A
`ChannelRegistry` class in `lib/src/channel_registry.dart`, exposing something like
`bumpEpoch()`, `forgetAll()` and `generationOf(name)`, would make `_generations` and
`_clientEpoch` genuinely unreachable from connect code rather than merely undeclared there.

Worth recording honestly: after 0.6.0, the one place where `_generation` and `_generations`
are both still in scope is `_ReverbConnect` — `disconnect`, `_open` and `_onDropped`. That is
exactly the code where confusing them is most likely and most damaging. The hazard is now
confined to one file instead of spread across four, which is a real improvement, but it is
not gone.

**Trigger:** a bug traced to confusing the three counters.

For calibration on how likely that is: the epoch races have been got wrong twice already,
both times caught in review before shipping — `117f636` ("close epoch gaps in
`disconnect(forget:)` missed by review") and `cf7091a` ("cover the whisper pass-through epoch
check"). Neither reached production. That is the argument for sealing them and also the
argument that the current arrangement, with its heavy comments, is holding: the defences that
caught those two were reading and review, and both still apply.

## Still open, and not code: the Android cleartext claim

`README.md`'s "Local development" section says Android's cleartext restrictions apply from
API 28 and hedges on whether they affect this package. The hedge is deliberate and remains
the only place in the documentation that says "may" where nobody has checked.

The restriction is enforced by `NetworkSecurityPolicy` in the Java networking stack, while
this package's socket comes from `web_socket_channel` → `dart:io`, which opens sockets from
the Dart VM. Whether that path consults the policy has never been established.

**The experiment:** `flutter run` a debug build against `ws://10.0.2.2:8080` on an API 28+
emulator with an unmodified `AndroidManifest.xml`. If it connects, the troubleshooting
checklist's item 2 is sending users after a phantom and should be softened further. If it
fails, the prose can state the mechanism outright instead of hedging.

Until someone runs it, the hedged wording stays.

## Permanently out of scope

Unchanged from the 0.4/0.5 roadmap, and not revisited:

- Encrypted channels (`private-encrypted-`) — Reverb has no server-side support.
- Pusher's hosted service, clusters, and API-key configuration.
- Client-side offline event replay — the server decides what a reconnecting client sees, and
  cache channels are Reverb's answer.
